# Technical evidence detection — first implementation

Stage 3 now detects thirteen evidence categories separately from source format, records source quotes/page/item provenance, assigns stable content-addressed IDs, and writes a separate `technical_evidence_ledger.json`. This derived ledger never records human corrections or changes the correction ledger. Rebuilding retains superseded records and refuses corrupt history.

Types: troubleshooting, alarm, diagnostic flowchart, operation, maintenance/repair, specification, safety/interlock, parts, circuits, inspection/test, maintenance schedule, component description and applicability/reference. Classification uses heading context and body clues; it is a candidate detector, not certified semantic understanding. Categories can overlap. Search headings/aliases are derived metadata, never added to source text. Lexical ranking gives an intent-based category bonus only after a source/term match; remaining evidence remains searchable. Existing indexes are annotated in memory without rewriting source books or vector contents.

An explicit fault/cause/remedy table parser stores complete rows with their literal source quote. Blank merged cells, ambiguous headers and graph relationships are not guessed. `source_bound` means literal text with page/item provenance; it is not human approval or proof that OCR is correct. A graph or sparse picture becomes `needs_visual_parse`, is not answer-eligible, and has no invented relationships.

Automatic ledger creation runs during Stage 3 build/reoptimization. Existing books can be scanned through `POST /api/postprocess/jobs/{id}/technical-evidence/detect` under their lifecycle lock. Read the ledger using `GET /api/postprocess/jobs/{id}/technical-evidence`. Both operations make zero model calls. A CPU CLI provides dry-run detection reports; `--write` is intended for offline snapshots only, not a concurrently running deployment.

Remaining work: automatic extraction of flowchart nodes/arrows with source image coordinates; independent visual verification; richer type-specific parsing for alarm/settings/procedure/part relationships; a review UI and semantic evaluation of extracted relationships. This release detects these gaps rather than claiming unread diagrams are solved. In particular Instruction Manual page 160 must report `needs_visual_parse` until its pixel content and branch links are extracted and checked.
